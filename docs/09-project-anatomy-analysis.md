# План исследования устройства 20 проектов

## Цель

До построения генератора нужно ответить не на вопрос «какие файлы лежат в папках», а на три независимых вопроса:

1. **Как организована поставка:** где результат проектирования, где исходная подоснова, где зависимости, ревизии и архивные копии.
2. **Как представлена территория:** существует ли единая координатная модель или проект собран из XREF, фрагментов, model-space листов либо только печатных layout/PDF.
3. **Как выражена семантика:** какие слои, блоки и типы объектов соответствуют ограничениям, существующему положению и проектным посадкам.

Результат исследования — не один универсальный парсер, который «угадывает всё», а наблюдаемый конвейер, типология поставок и набор адаптеров для реально найденных семейств проектов.

## Основной принцип: сначала граф проекта, затем геометрия, затем семантика

Анализ всех DXF как равноправных файлов даст ложную картину. Один и тот же файл может встречаться в рабочей папке, архиве и составе eTransmit; XREF не является самостоятельным проектным решением; старый вариант может иметь более убедительное имя, чем актуальная голова.

Порядок работы:

```text
манифест поставки
  → роли файлов и версии
  → граф master/XREF/derived
  → пространственная структура и листы
  → профили слоёв/блоков/entities
  → каноническая семантика
  → типология 20 проектов
```

Текущий корпус содержит 1 251 опубликованный DXF-путь: 819 обычных и 432 извлечённых из архивов. При этом 374 архивных пути байт-в-байт совпадают с уже обработанными файлами; архивы добавляют только 58 новых уникальных SHA-256. Дубликаты сохраняют provenance поставки, но не должны повторно влиять на статистику CAD-методик.

## Плоскость 1. Организация поставки

### Что считать «исходными данными»

Название каталога не является достаточным доказательством роли. Предварительная онтология:

| Каноническая роль | Примеры содержимого | Использование системой |
|---|---|---|
| `delivery_master` | генплан, сводный/посадочный план, главный файл комплекта | кандидат на точку входа |
| `delivery_derived` | дендроплан, разбивочный план, план покрытий, ведомость | референс и проверка результата |
| `xref_dependency` | геоподоснова, сети, борта, здания, внешние ссылки | обязательная зависимость master |
| `survey_source` | ИГДИ, топосъёмка, геодезия, инвентаризация | источник существующего положения и ограничений |
| `boundary_source` | границы работ, кадастр, красные линии | область анализа или ограничение |
| `documentary_source` | ТЗ, согласования, PDF, XLSX, ведомости | контекст и контрольные данные |
| `visual_source` | фотографии, схемы, сканы | доказательный материал, не точная геометрия |
| `revision_or_archive` | старые выдачи, eTransmit, ZIP/RAR/7z | история и альтернативная версия |
| `unknown` | неоднозначный файл | ручное/LLM-ревью |

«Исходные данные» даны не только «для веса» и не обязательно для обучения модели. Они позволяют:

- восстановить отсутствующие XREF главного чертежа;
- понять существующие коммуникации и объекты, относительно которых действуют отступы;
- проверить границу работ и систему координат;
- отличить уже запроектированные растения от существующих;
- восстановить методику подрядчика и проверить итоговый лист.

Система не обязана редактировать эту подоснову, но обязана знать, какие ограничения из неё были прочитаны, а какие зависимости отсутствуют.

### Автоматический анализ организации

Для каждого файла фиксируем:

- относительный путь, SHA-256, размер, формат и CAD-версию;
- находится ли он в архиве и с каким исходным архивом связан;
- имена model/layout, `$INSUNITS`, `$EXTMIN/$EXTMAX`, число слоёв/блоков/entities;
- XREF, IMAGE/PDF underlay, font/plot-style зависимости;
- временные метки и признаки версии в имени;
- текстовые маркеры из имени, layout, title block и атрибутов.

Затем строим ориентированный граф:

```text
master candidate ──XREF/underlay/relative path──▶ dependency
        │
        ├──derived-from/name/revision──▶ alternate delivery
        └──layout/export evidence──────▶ PDF sheet
```

LLM получает только компактные карточки неоднозначных файлов и предлагает роль с evidence. Она не назначает `delivery_master` без подтверждения графом зависимостей, содержимым title block или человеком.

### Артефакты плоскости 1

- `project-manifest.json` — все физические и виртуальные архивные пути;
- `file-roles.json` — роль, confidence и evidence;
- `dependency-graph.json` — XREF/underlay/derived/revision связи;
- `entrypoint-candidates.json` — ранжированные головы проекта;
- `missing-dependencies.json` — неразрешённые ссылки;
- `project-organization.md` — понятный человеку разбор поставки.

## Плоскость 2. Единая территория или набор листов

Нужно раздельно анализировать четыре пространства:

1. **Model space** — инженерная координатная модель.
2. **Paper space/layout** — оформление печатных листов и viewport в model space.
3. **XREF assembly** — модель, собранная вставками из нескольких файлов.
4. **PDF sheets** — производное печатное представление, иногда единственный доступный источник.

Разбиение PDF на листы не означает, что CAD тоже фрагментирован. Наиболее вероятный нормальный случай: одна цельная территория в model space, несколько layout с viewport и несколько PDF-листов. Поэтому PDF нельзя склеивать до проверки model space и XREF.

### Автоматические проверки

Для каждого master-кандидата:

- вычислить extents model space без paper-space рамок;
- отдельно вычислить extents каждого layout и параметры viewport;
- найти прямоугольные рамки, штампы, марки стыка и номера листов;
- извлечь INSERT/XREF-трансформации `translate / rotate / scale`;
- построить spatial index и устойчивые к выбросам кластеры геометрии;
- проверить единицы, масштаб, вращение, Z-диапазон и удалённые выбросы;
- сопоставить PDF-листы с layout по имени, штампу, размеру и тексту;
- создать быстрые растровые превью model space, layouts и пространственных кластеров.

### Классификация пространственного устройства

Каждый проект получает один основной тип и дополнительные признаки:

| Тип | Значение |
|---|---|
| `single_model` | территория целиком находится в model space одного master |
| `xref_assembly` | цельная сцена получается после разрешения XREF |
| `multi_file_tiles` | территория поделена между несколькими CAD-файлами в общей системе координат |
| `model_space_sheets` | листы физически разнесены в model space и требуют выделения viewport/рамок |
| `layout_only_evidence` | содержательная модель доступна преимущественно через layouts |
| `pdf_only_fragments` | CAD недостаточен, требуется геопривязка PDF-фрагментов |
| `unregistered_fragments` | общей трансформации пока нет; автоматическая генерация блокируется |

### Gate для «цельного плана»

Проект считается собранным, только если:

- известны рабочие единицы;
- разрешены критичные XREF либо явно описаны отсутствующие;
- для всех фрагментов известны матрицы преобразования;
- overlap/gap между стыкуемыми частями объяснён;
- минимум две контрольные точки подтверждают каждую ручную трансформацию;
- RMS-ошибка и источник привязки записаны;
- preview цельной сцены прошёл визуальное ревью.

Нельзя склеивать фрагменты только потому, что их рамки похожи или PDF-листы визуально продолжают друг друга.

### Артефакты плоскости 2

- `cad-spaces.json` — model/layout/viewports/extents;
- `transforms.json` — XREF и ручные трансформации;
- `spatial-clusters.geojson` — компоненты и выбросы;
- `sheet-map.json` — связь layout/PDF/рамка/участок модели;
- `previews/` — model, layouts, assembled scene;
- `assembly-status.json` — тип проекта, completeness и blockers.

## Плоскость 3. Слои и объекты DXF

Имя слоя — только один сигнал. Семантика определяется комбинацией:

- имя и описание слоя;
- типы entities и их количество;
- цвет, linetype, lineweight и plot-флаги;
- используемые block definitions и атрибуты;
- повторяющиеся тексты/обозначения;
- геометрическая форма и размер объектов;
- соседство с другими объектами;
- роль файла в графе проекта;
- легенда листа и ведомости.

### Профиль каждого CAD-файла

Собираем без изменения DXF:

- layers и статистику entities по каждому слою;
- `LINE/LWPOLYLINE/POLYLINE/ARC/CIRCLE/HATCH/SPLINE/TEXT/MTEXT/INSERT/...`;
- блоки, вложенные блоки, атрибуты и частоту вставок;
- proxy/custom objects и unsupported-классы;
- 2D/3D-признаки, elevation и Z-выбросы;
- bbox, длину, площадь и характерные размеры;
- текстовый словарь слоя, блоков, атрибутов и легенд;
- fingerprint геометрии для поиска дубликатов и ревизий.

### Канонический словарь v1

Минимальные классы для генератора:

- граница работ и иные территории;
- здания/сооружения;
- проезжая часть, борта, тротуары и покрытия;
- надземные и подземные коммуникации по типам;
- существующие деревья/кустарники/газон;
- удаляемая и пересаживаемая растительность;
- проектные деревья/кустарники/цветники;
- рельеф и отметки;
- служебные рамки, штампы, размеры, подписи и легенды;
- неизвестное ограничение (`unknown_constraint`) и неизвестная декорация.

### Каскад классификации

1. Подтверждённый mapping конкретного подрядчика/шаблона.
2. Точные правила по имени слоя, блока и атрибутам.
3. Геометрические и стилевые признаки.
4. Словарь, извлечённый из легенды/ведомости.
5. LLM-кандидат на компактной `layer-card`, содержащей статистику и примеры текста.
6. Ручное подтверждение неоднозначных или safety-critical классов.

LLM не получает гигантский сырой DXF и не решает, допустима ли посадка. Она помогает сопоставлять неизвестную терминологию с каноническим словарём. Один и тот же слой может иметь разные значения в файлах с разными ролями.

### Артефакты плоскости 3

- `cad-profile.json` — полный машинный профиль файла;
- `layer-catalog.csv` — компактная таблица слоёв;
- `block-catalog.csv` — блоки и атрибуты;
- `layer-cards.jsonl` — вход для правил/LLM;
- `layer-mapping.yaml` — утверждённая семантика и confidence;
- `unknowns.json` — объекты, блокирующие автоматический расчёт.

## Как пройти от двух пилотов к двадцати проектам

### Этап 0. Зафиксировать корпус

- использовать SHA-256, а не количество путей, для статистики форматов;
- оставить архивные дубликаты в provenance, но не анализировать их повторно;
- отделить текущую поставку, архивные ревизии и производные DXF;
- назначить стабильные `project_id`, `asset_id`, `content_id`.

**Gate:** один и тот же байтовый файл имеет один `content_id`, но может иметь несколько `asset_id`.

### Этап 1. Построить быстрый CAD-profiler

Первый инструмент ничего не классифицирует и не склеивает. Он только извлекает header/tables/layouts/XREF/entities/blocks/extents/text tokens и создаёт preview. Запускаем его на всех уникальных DXF, но тяжёлую детализацию сначала только на master-кандидатах.

**Gate:** профиль создаётся воспроизводимо, ошибки парсера и proxy-объекты видны отдельно.

### Этап 2. Глубоко разобрать два контрастных пилота

1. **Песчаный переулок:** главный файл, пропавшие/найденные XREF, архивный eTransmit, листовая структура. Первичный ground truth совместного просмотра с архитектором зафиксирован в [отдельном кейсе](project-research/01-peschanaya-architect-review.md).
2. **Куликовская улица:** много дисциплин, генплан, благоустройство, линейные/дуговые посадки, ведомость.

Для каждого вручную подтверждаем голову, dependency graph, единую сцену и layer mapping. Никаких общих эвристик не добавляем без фикстуры из реального файла.

**Gate:** по одному утверждённому `project-card` и assembled preview на пилот.

### Этап 3. Без ручной подгонки просканировать остальные 18

Получаем матрицу расхождений:

- организация каталогов и naming;
- число master-кандидатов и глубина XREF;
- пространственный тип;
- словарь слоёв/блоков;
- layouts/PDF-соответствие;
- недостающие зависимости и proxy-классы;
- доля семантики, покрытая пилотными правилами.

Не исправляем каждый объект прямо в коде. Сначала группируем проекты по сходству.

### Этап 4. Выделить семейства подрядчиков/методик

Кластеризация строится по четырём профилям:

1. дерево поставки и роли папок;
2. XREF/dependency graph;
3. spatial/layout pattern;
4. нормализованный словарь слоёв, блоков и entity types.

Ожидаемый результат — несколько повторяющихся семейств и небольшой хвост уникальных случаев, а не двадцать отдельных импортёров. Для каждого семейства создаётся адаптер конфигурации, тестовые файлы и явные исключения.

### Этап 5. Повторный прогон всех 20

После добавления адаптеров снова запускаем неизменённый корпус и сравниваем метрики. Новая эвристика принимается, только если улучшает целевой класс и не ломает уже утверждённые пилоты.

## Сводная матрица 20 проектов

Итоговый отчёт имеет одну строку на проект:

| Поле | Смысл |
|---|---|
| `organization_family` | тип структуры поставки |
| `entrypoint` | подтверждённая голова или `unknown` |
| `dependency_completeness` | доля разрешённых критичных ссылок |
| `spatial_type` | один из типов представления территории |
| `units/crs` | доказанные единицы и статус системы координат |
| `model_complete` | можно ли собрать цельную сцену |
| `layer_family` | найденный словарь/шаблон подрядчика |
| `semantic_coverage` | доля entities с утверждённым классом |
| `critical_unknowns` | неизвестные потенциальные ограничения |
| `automation_status` | `ready / needs_review / blocked` |

## Что реализуем первым

1. Команду `profile-dxf` и схему `cad-profile.json`.
2. Агрегатор `profile-project`, строящий file-role и dependency candidates.
3. Генератор model/layout/XREF previews.
4. Глубокий разбор Песчаного и Куликовской с ручным ground truth.
5. Batch-профилирование уникального корпуса и сводную матрицу 20 проектов.
6. Только после этого — LLM layer mapper и механизм адаптеров семейств.

Такой порядок сначала отвечает на вопрос «что является проектом», затем «где находится цельная территория» и лишь после этого «что означают её объекты». Это предотвращает обучение эвристик на архивных дублях, штампах листов и XREF, ошибочно принятых за самостоятельные планы.
