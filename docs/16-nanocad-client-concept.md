# Возможный клиент GreenPlan для nanoCAD

- Status: Idea / backlog
- Date: 2026-09-25
- Architecture boundary: [ADR-0007](adr/0007-web-application-boundaries.md)

## Идея

В дополнение к браузерному workspace можно разработать тонкое приложение для nanoCAD на C#/.NET API. Оно даст проектировщику доступ к GreenPlan непосредственно внутри привычной CAD-среды, но не станет отдельной реализацией предметного и геометрического движка.

```text
nanoCAD + GreenPlan .NET plugin
             │ HTTPS / OpenAPI
             ▼
        FastAPI domain API
             │
      jobs / PostGIS / artifacts
```

## Возможности клиента

- связать открытый DWG/DXF с project, source artifact и revision;
- загрузить файл через intake либо проверить его hash и найти уже импортированную версию;
- запустить анализ, построение ограничений и генерацию посадок;
- отображать статус фоновой задачи;
- загрузить опубликованный результат и создать/обновить выделенные слои `GREEN_AI_*`;
- выбирать посадку или нарушение в чертеже и получать нормативное объяснение;
- переходить по deep link к тому же объекту в web workspace;
- передавать пользовательские изменения обратно только как новый source artifact/revision.

## Предпочтительная технология

Первый spike следует делать на C# и .NET API nanoCAD: это наиболее прямой путь к командам, палитрам, документу и CAD-объектам при сохранении обычного HTTP-клиента к FastAPI. NRX/C++ нужен только если .NET API не даст требуемой производительности или доступа к необходимым примитивам.

COM/ActiveX допускает внешнюю автоматизацию, в том числе из Python, но не поддерживается под Linux и поэтому не является основой клиента для МосТех.ОС. LISP остаётся вариантом для небольших локальных команд и пакетных сценариев, но не для основного интеграционного UI.

SDK, примеры и точные условия распространения необходимо получить через клуб разработчиков nanoCAD и проверить для конкретной версии продукта. Расширенные функции модулей «Топоплан» и «Землеустройство» могут потребовать отдельную лицензию TopoAPI; базовый spike не должен от них зависеть.

## Архитектурные ограничения

- плагин не обращается к PostGIS напрямую;
- нормативные правила, spatial queries и генерация остаются в FastAPI/domain services;
- обмен выполняется через версионированный OpenAPI и опубликованные артефакты;
- отсутствие плагина не блокирует основной сценарий `DXF → pipeline → DXF`;
- загрузка DLL и версия SDK не должны становиться зависимостью серверных контейнеров;
- собственные непрозрачные CAD-примитивы не используются в обязательном DXF-результате без доказанного fallback;
- результат, изменённый в nanoCAD, не перезаписывает approved revision и повторно проходит intake/provenance.

## Spike перед включением в фазу разработки

1. Выбрать точную версию nanoCAD под Windows и/или МосТех.ОС и получить соответствующий SDK.
2. Собрать минимальную .NET DLL с командами `GREENLOGIN`, `GREENPROJECT` и `GREENREFRESH`.
3. Прочитать путь документа, слои, handle выбранного объекта и custom metadata.
4. Вызвать тестовый FastAPI endpoint и корректно обработать timeout, отмену и несовместимую версию API.
5. Создать отдельный слой и тестовые entities, сохранить DXF, закрыть и повторно открыть его.
6. Проверить сохранность исходных слоёв, handles/provenance mapping и читаемость результата другим DXF-viewer.
7. Зафиксировать лицензионные условия разработки, поставки и эксплуатации плагина.

Успешный spike станет основанием для отдельного ADR и phase plan. До этого nanoCAD-клиент остаётся опциональным backlog-направлением, а не обязательством MVP.
