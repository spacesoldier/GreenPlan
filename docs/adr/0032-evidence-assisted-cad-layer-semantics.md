# ADR-0032 — Контекстная классификация CAD-слоёв с инженерной обратной связью

- Status: Proposed
- Date: 2026-09-28
- Owners: CAD domain, ML, backend, data platform
- Related: ADR-0020, ADR-0022, ADR-0023, ADR-0030

## Context

Имена CAD-слоёв не образуют надёжного классификатора сами по себе. Подрядчики используют собственные
сокращения, транслитерацию, смесь кириллицы и латиницы, номера комплектов и локальные аббревиатуры.
Одинаково названные слои могут иметь разный смысл, а кабельная сеть может быть обозначена коротким
кодом, понятным только в контексте файла, XREF-ветки и соседних объектов.

Текущий Laya-provider полезен как экспериментальный источник подсказок, но его zero-shot решения
недостаточно точны. При этом инженер уже может находить опорные примеры: слой с кабельными сетями
подтверждён как `utility`. Такие решения нельзя терять — это размеченные свидетельства, на которых
должна строиться следующая подсказка.

## Decision

### 1. Классифицируем не строку, а наблюдение слоя

Worker получает версионированный `cad-layer-observation-v2`:

- исходное и нормализованное имя слоя;
- разбиение на токены, транслитерацию, кириллическо-латинские омографы;
- варианты расшифровки сокращений из версионированного словаря;
- путь, смысловую ветку поставки и предполагаемую роль DWG/DXF;
- лист/Model, XREF-родителей и XREF-потомков;
- типы, количество и диапазоны размеров примитивов, цвет, linetype и block names;
- соседние слои и уже подтверждённые категории того же файла;
- ближайшие подтверждённые человеком примеры из этого проекта, подрядчика и всего корпуса.

Сырой DWG и полная геометрия в prompt не передаются. Признаки должны быть воспроизводимы и храниться
с версией extractor-а.

### 2. Перед моделью работает детерминированный поиск

Pipeline выполняется в следующем порядке:

1. exact match по подтверждённой сигнатуре слоя;
2. поиск семейства после нормализации имени и entity signature;
3. retrieval похожих подтверждённых примеров;
4. правила терминов и сокращений;
5. модель ранжирует только разрешённые категории taxonomy;
6. калибратор решает: показать top-3 либо воздержаться как `unknown`.

Подтверждённый пример кабельной сети категории `utility` становится exemplar, но не глобальным
правилом по одному имени. Автоматическое распространение допустимо только для совпавшей сигнатуры и
явно показывается инженеру.

### 3. Ответ модели строго типизирован

Provider обязан вернуть JSON со следующими полями:

- `taxonomy_version`, `category`, `confidence`;
- до трёх `alternatives`;
- `matched_exemplars` и использованные признаки;
- краткое `rationale`, не считающееся доказательством;
- `abstained` и причина отказа от классификации;
- `provider`, `model`, `weights_revision`, `prompt_schema_version`.

Свободно придуманная категория отклоняется. Подсказка никогда не меняет effective mapping без
подтверждения инженером.

### 4. Модели имеют разные роли

Новые модели Яндекса рассматриваются не как безусловная замена Laya, а как кандидаты разных классов:

| Кандидат | Размер и CPU | Роль в системе |
|---|---|---|
| `AliceAI-Foundation-80B-A3B-Base` | 80B всего, 3B активных; BF16 около 160 GB весов. Даже при 4-bit теоретически около 40 GB до runtime overhead. Официальный пример vLLM использует четыре GPU | offline teacher, генерация вариантов расшифровок и benchmark на GPU; не основной CPU worker |
| `AliceAI-T5-35B-A0.6B` | 34,35B уникальных параметров; BF16 около 69 GB. Официальный пример использует CUDA и custom code | экспериментальный encoder/teacher после отдельной проверки quantization и CPU backend |
| `YandexGPT-5-Lite-8B-instruct-GGUF Q4_K_M` | готовый GGUF 4,92 GB, официальный запуск через llama.cpp | практический CPU-кандидат для локального сравнительного стенда |
| Laya | уже подключён и лёгок, но слаб на текущем zero-shot корпусе | baseline до прохождения нового кандидата через одинаковый benchmark |

`active parameters` определяют вычисления на токен, но не отменяют необходимость разместить все
экспертные веса. Поэтому AliceAI 80B не объявляется CPU-ready только из-за маркировки A3B.

Лицензия AliceAI Foundation — Apache-2.0. У YandexGPT-5-Lite собственная лицензия
`yandexgpt-5-lite-8b`; до включения в распространяемую сборку требуется отдельная юридическая
проверка. Загрузка модели в Compose не производится этим ADR.

### 5. Обратная связь образует датасет, а не меняет веса онлайн

Каждое accept/reject хранится как неизменяемое review-событие с observation snapshot, предложением,
выбранной категорией, пользователем и версиями taxonomy/model. Из этих событий строится dataset
release. Дообучение, обновление словаря и калибровка выполняются отдельной воспроизводимой job;
production weights во время review не мутируют.

Train/test split делается по проектам и подрядчикам, а не случайно по строкам: иначе одинаковые
локальные сокращения протекут в test и дадут ложное качество.

### 6. Внедрение проходит через сравнительный стенд

Один и тот же corpus прогоняется через rules, Laya и CPU-кандидата. Сохраняются:

- top-1 и top-3 accuracy;
- precision и coverage при порогах уверенности;
- confusion matrix по верхним категориям;
- доля корректных abstain;
- latency p50/p95, peak RSS, размер weights и время cold start;
- качество отдельно на неизвестных подрядчиках и неизвестных сокращениях.

Автопринятие запрещено до согласованного порога. Для прототипа модель только предлагает варианты;
при низкой уверенности интерфейс честно показывает `unknown`.

## Consequences

- качество растёт от инженерных подтверждений, а не от усложнения prompt-а;
- подсказку можно объяснить похожими слоями и признаками;
- замена модели не меняет API, БД и workflow review;
- большие AliceAI-модели не блокируют локальную CPU-разработку;
- потребуется выделить сущности observation, exemplar, dataset release и evaluation run;
- категории `utility` недостаточно для правил посадки: следующий уровень taxonomy должен различать
  кабель, газ, водоснабжение, теплосеть и другие виды сетей.

## Verification

- слой без понятного имени получает контекст файла, XREF и entity types;
- подтверждённый кабельный exemplar попадает в retrieval следующего запуска;
- тестовый проект/подрядчик отсутствует в train split;
- provider не может сохранить категорию вне taxonomy;
- low-confidence ответ сохраняется как abstain, а не как уверенная классификация;
- benchmark сообщает peak RSS и latency на целевой CPU-машине;
- UI показывает model/version, confidence, признаки и похожие подтверждённые примеры;
- смена provider не меняет уже принятые инженером mappings.
