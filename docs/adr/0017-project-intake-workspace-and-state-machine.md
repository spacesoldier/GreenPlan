# ADR-0017: Проект начинается с управляемой приёмки файлов

- Status: Accepted
- Date: 2026-09-27
- Owners: product, frontend, backend, CAD ingestion
- Related phase: Phase 3
- Supersedes: —
- Superseded by: —

## Context

Текущий интерфейс открывает две заранее импортированные улицы и позволяет переключаться между ними. Пользователь не может создать проект, загрузить поставку, увидеть состав файлов, выбрать точку входа или понять, на каком этапе исходные данные стали канонической моделью.

Разбор Песчаного переулка с архитектором показал, что один проект содержит несколько master-кандидатов, model space, paper-space layouts, XREF, ведомости и разные предметные состояния. Автоматический переход от одного выбранного DXF прямо к viewer скрывает неполноту данных и создаёт ложное впечатление готовой сцены.

## Decision

### Intake workspace

Перед существующим viewer появляется отдельный пользовательский процесс:

```text
список проектов
  → создание проекта
  → загрузка поставки
  → инвентаризация
  → анализ CAD и зависимостей
  → fidelity review
  → публикация канонической ревизии
  → 2D/3D workspace
```

Создание проекта и загрузка файлов не публикуют каноническую модель автоматически.

### Экраны

1. **Projects home** — проекты, состояние последней ревизии, проблемы и кнопка «Новый проект».
2. **Create project** — название, код, территория, описание и пустая draft revision.
3. **Delivery upload** — загрузка файлов, папки либо архива с сохранением относительных путей.
4. **Inventory** — дерево поставки, реальные форматы, размеры, хеши, дубликаты, архивные члены и кандидаты ролей.
5. **Processing run** — наблюдаемый граф стадий direct-read/conversion/profile/XREF/audit с логами и повторным запуском.
6. **Fidelity review** — сравнение исходника и производного представления, missing XREF, layouts, entity diff и preview.
7. **Assembly review** — выбор master/головы, разрешение неоднозначных ссылок и подтверждение состава сцены.
8. **Project workspace** — существующий viewer только для опубликованной или явно preview-ревизии.

Один проект может иметь несколько deliveries и revisions. Новая загрузка не перезаписывает предыдущую.

### State machine

Ревизия приёмки проходит состояния:

```text
draft
  → receiving
  → inventoried
  → analyzing
  → review_required
  → ready_to_publish
  → published
```

Дополнительные состояния: `blocked`, `failed`, `retired`. Переходы выполняются сервером и записываются в audit log. Возобновление или retry создаёт новую попытку стадии, но не теряет исходный лог.

### Storage boundaries

- загруженные байты неизменяемы и адресуются SHA-256;
- пользовательский путь хранится отдельно от content identity;
- raw delivery хранится вне `work/jobs`;
- `work/jobs` остаётся временным рабочим каталогом конкретного запуска;
- архив распаковывается в sandbox с лимитами размера, числа членов и глубины;
- симлинки и path traversal не следуются;
- БД хранит метаданные, состояния, provenance и ссылки на артефакты, а не крупные CAD-файлы как `bytea`.

Для прототипа content-addressed store располагается в примонтированном каталоге `platform/data/intake/`. Возможный object storage является заменяемой реализацией того же контракта.

### API and frontend boundary

Next.js остаётся UI/BFF согласно ADR-0007. Загрузка идёт streaming multipart без буферизации полного DWG в памяти Next.js. Для локального прототипа BFF проксирует поток в FastAPI; для крупного production storage может использоваться короткоживущий upload grant без выдачи внутренних credentials браузеру.

Folder upload сохраняет browser relative path. Сервер никогда не доверяет ему как реальному filesystem path.

## Alternatives considered

### Оставить проекты конфигурацией администратора

Отклонено: не позволяет архитектору увидеть ошибки поставки и превращает каждый новый проект в ручную операцию разработчика.

### Сразу открывать первый найденный DWG/DXF

Отклонено: имя и порядок файлов не доказывают роль master, полноту XREF и предметное состояние.

### Перезаписывать текущую ревизию новой загрузкой

Отклонено: исчезают provenance, воспроизводимость и возможность сравнить исправленную поставку с предыдущей.

### Хранить загрузки внутри job directory

Отклонено: job является удаляемой рабочей областью и не может быть первичным хранилищем исходника.

## Consequences

### Positive

- новый проект можно создать без ручной подготовки БД;
- пользователь видит путь от поставки до сцены;
- исходные данные, производные файлы и публикации разделены;
- повторная загрузка и retry воспроизводимы;
- неполный проект не маскируется под готовый viewer.

### Negative / trade-offs

- до открытия карты появляется обязательный intake flow;
- требуется управление файловым хранилищем, квотами и очисткой временных данных;
- frontend должен отображать долгие асинхронные стадии и частичные ошибки;
- существующие два пилота нужно зарегистрировать как исторические deliveries.

## Verification

- новый проект создаётся через UI и получает draft revision;
- папка сохраняет относительную структуру без принятия опасных путей;
- повторная загрузка одинаковых байтов дедуплицируется по SHA-256;
- новая delivery не меняет опубликованную ревизию;
- browser refresh восстанавливает текущий run из API;
- failed stage можно повторить без удаления первого лога;
- viewer недоступен как effective model до принятого fidelity gate;
- browser bundle не содержит storage/DB credentials.
