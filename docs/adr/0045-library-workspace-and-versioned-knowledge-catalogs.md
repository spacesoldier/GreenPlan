# ADR-0045: Раздел «Библиотека» и версионируемые каталоги знаний

- Status: Accepted
- Date: 2026-09-29
- Owners: product / domain / web
- Related phase: Phase 4, iteration 2
- Supersedes: —
- Superseded by: —

## Context

Главная страница GreenPlan сейчас ориентирована на проекты: пользователь создаёт карточку проекта и проходит мастер подготовки материалов. Но нормативы, принципы генерации и каталог растений не принадлежат одной улице. Это общесистемные версионируемые знания, используемые несколькими проектами. Если спрятать их внутри проекта или представить несвязанными таблицами, нельзя будет понять, какой набор знаний породил предложение по озеленению.

Три вида знаний различаются по юридическому и вычислительному смыслу:

- нормативные правила задают обязательные или рекомендательные ограничения и требуют provenance;
- принципы генерации описывают проектные стратегии, например кустарники вдоль подходящего контура и деревья внутри доступной зоны;
- растения описывают биологические профили, требования и доступные CAD-обозначения.

## Decision

На главной странице рядом с гридом проектов появляется самостоятельный раздел «Библиотека». Он открывает workspace с тремя верхнеуровневыми экранами:

1. `Правила и документы` — нормативные документы, редакции, сегменты, кандидаты правил, утверждённые правила и rule sets.
2. `Принципы генерации` — версионируемые стратегии размещения и их параметры, области применимости, входные данные и используемые ограничения.
3. `Библиотека растений` — таксоны, профили растений, стадии роста, размеры, требования к среде и уходу, источники данных и CAD-символы.

Канонические маршруты: `/library/regulations`, `/library/generation-principles`, `/library/plants`. Next.js получает данные только через BFF/FastAPI, не подключается к PostGIS напрямую.

Основной объект представления — карточка с краткой сводкой, статусом, версией и provenance. Карточка открывает детальный inspector. Все каталоги поддерживают текстовый поиск, фильтры статуса и типа, сортировку и deep link. Серверная пагинация обязательна для потенциально больших коллекций.

Общие состояния знаний: `draft`, `needs_review`, `approved`, `retired`; нормативные сущности сохраняют более точные существующие статусы там, где это необходимо. Карточка всегда показывает, что является исходным материалом, результатом модели или решением человека.

Принцип генерации хранится отдельно от нормативного правила. Его версия фиксирует:

- тип стратегии и алгоритм;
- входные и выходные классы объектов;
- параметры шага, отступов, плотности и ориентации;
- ссылки на применимые rule sets;
- фильтр подходящих plant profiles;
- версию реализации и набор тестовых сценариев.

Публикация проекта фиксирует ссылки на версии rule set, generation principle set и plant catalog snapshot. Последующее обновление библиотеки не меняет уже опубликованный результат скрытно.

## Alternatives considered

### Хранить библиотеку внутри каждого проекта

Отклонено: появляются копии, расходящиеся версии и невозможность централизованной проверки знаний.

### Один смешанный каталог карточек

Отклонено: юридическое правило, эвристика размещения и биологический профиль имеют разные жизненные циклы и уровни доверия.

### Показывать только административные таблицы

Отклонено: для проверки источников, статусов и взаимосвязей нужен предметный workspace, а не представление схемы БД.

## Consequences

### Positive

- пользователь видит общую базу знаний отдельно от проектных поставок;
- генерация становится воспроизводимой по снимкам трёх каталогов;
- карточки дают понятную точку входа для review и каталогизации;
- новые источники и стратегии можно добавлять без изменения структуры проекта.

### Negative / trade-offs

- необходимы отдельные API, права доступа и состояния review;
- интерфейс обязан ясно различать закон, проектную эвристику и биологический факт;
- snapshot/version semantics усложняют публикацию, но исключают скрытый drift.

## Verification

- с главной страницы можно открыть каждый из трёх каталогов без выбора проекта;
- карточка показывает статус, версию и provenance, а URL восстанавливает выбранный объект;
- фильтры и пагинация выполняются сервером;
- draft-кандидат модели визуально и по API не маскируется под approved knowledge;
- опубликованный проект ссылается на неизменяемые версии всех использованных каталогов.
