# Офлайн-контуры зданий из OpenStreetMap

## 1. Роль OSM в системе

OpenStreetMap используется как воспроизводимый внешний векторный источник для восстановления контекста, прежде всего контуров зданий, которых нет в проектной поставке. Это не геодезическая съёмка и не безусловный источник истины: полнота, дата и точность различаются по территории.

OSM не заменяет CAD, инженерно-геодезические изыскания или официальную муниципальную геоподоснову. Он:

- заполняет отсутствующие контуры зданий и другие фоновые объекты;
- помогает привязать локальный CAD-план к местности как дополнительное свидетельство;
- даёт окружение для 3D-сцены и навигации;
- создаёт кандидаты ограничений, требующие проверки при safety-critical расчётах.

Порядок доверия по геометрии: подтверждённая геодезическая/CAD-геометрия → официальный геопортал с известной точностью и лицензией → OSM → геопривязанный PDF → ручная оцифровка/растровая подложка. Порядок может быть переопределён для конкретного проекта, но это должно быть записано в его политике сборки.

## 2. Почему именно сырой OSM, а не картографические тайлы

Для офлайн-контура загружается векторный extract в `.osm.pbf`, а не изображения тайлов. PBF компактен, содержит OSM-объекты и теги и может быть повторно импортирован без сети. Каждый использованный файл сохраняется или адресуется как неизменяемый артефакт с SHA-256.

Работа сервиса во время проектирования не требует доступа к сети. Обновление — отдельная управляемая операция: новый снимок OSM создаёт новую версию внешнего набора, после чего выполняются сравнение и повторное согласование, а опубликованная canonical model не меняется.

Для первого прототипа:

1. получить региональный PBF, содержащий все 20 территорий;
2. сохранить URL, время получения, timestamp набора, размер и SHA-256;
3. импортировать только необходимые объекты через `osm2pgsql` Flex в отдельную staging-схему PostGIS;
4. вырезать данные по буферизованной границе каждого проекта уже средствами PostGIS;
5. построить кандидатов зданий и выполнить conflation с проектными источниками;
6. опубликовать подтверждённый результат в новой canonical model.

Грубый `bbox` при импорте не используется как окончательный clip: на границе extract можно потерять части multipolygon. Региональный снимок должен иметь запас вокруг территории.

## 3. Что импортировать

Минимальный Flex-профиль сохраняет:

- `building=*` — общий контур здания;
- `building:part=*` — части здания, обычно различающиеся объёмом или высотой;
- OSM type (`node`, `way`, `relation`) и OSM id;
- все исходные теги в `jsonb`;
- исходную геометрию до исправлений;
- вычисленную валидную геометрию и журнал исправления;
- `height`, `min_height`, `building:levels`, `building:min_level`, `roof:*`, если они присутствуют.

Теги высоты и этажности считаются неподтверждёнными атрибутами. Они подходят для черновой 3D-массы, но не становятся проектной отметкой без другого evidence.

Контур `building=*` и `building:part=*` нельзя считать независимыми соседними зданиями. Общий outline описывает здание в целом, parts — его объёмные части. Импортёр сохраняет обе геометрии и связи, а представление для расчёта выбирает одну стратегию:

- footprint препятствия — общий outline, если он корректен;
- объединение parts — только если outline отсутствует или признан непригодным;
- 3D-визуализация — parts при достаточных тегах, иначе extrusion outline;
- пересекающиеся parts не суммируются как отдельные площади озеленения.

## 4. Модель данных

OSM находится в provenance/staging, а не непосредственно в `geo.spatial_objects`.

### `provenance.external_datasets`

Один неизменяемый снимок внешнего набора:

```text
id uuid primary key
provider text                 -- openstreetmap
dataset_name text             -- region/extract name
snapshot_at timestamptz null  -- дата данных, если известна
retrieved_at timestamptz
source_url text
media_type text               -- application/vnd.openstreetmap.data+pbf
sha256 text
license_code text             -- ODbL-1.0
license_url text
attribution_text text
coverage geometry(MultiPolygon, 4326) null
importer_name text
importer_version text
import_config_hash text
status text                   -- registered/imported/failed/retired
```

### `provenance.external_features`

Неизменённая адресуемая сущность провайдера:

```text
id uuid primary key
dataset_id uuid not null
provider_type text            -- node/way/relation
provider_id bigint not null
provider_version integer null
feature_kind text             -- building/building_part/etc.
tags jsonb not null
source_geom geometry(Geometry, 4326)
validity_status text
```

Уникальность: `(dataset_id, provider_type, provider_id)`. Если extract не содержит `provider_version`, поле остаётся `NULL`, а воспроизводимость обеспечивают SHA-256 всего PBF и конфигурация импорта.

### Связь с канонической моделью

Для OSM `provenance.source_assets` ссылается на запись external dataset, а `source_fragments` — на external feature. Обычная `provenance.object_evidence` связывает feature с `structure.building` и хранит:

- `evidence_role`: `existence`, `geometry`, `attribute` или `contradiction`;
- метод совмещения и `transform_id`;
- исходный и итоговый confidence;
- метрики смещения/перекрытия;
- решение `accepted_reference`, `candidate`, `conflict`, `stale` или `rejected`;
- автора/процесс и время решения.

Канонический объект получает собственный UUID. OSM id остаётся внешним идентификатором evidence и никогда не становится primary key предметной модели.

## 5. Координаты и совмещение с CAD

OSM-геометрия хранится в WGS 84 (`EPSG:4326`) как источник. Для метрических операций она преобразуется в доказанную проектную CRS. Web Mercator не используется для точных расстояний.

Если CAD находится в локальной системе без известной связи с глобальной CRS, наличие похожих зданий ещё не доказывает трансформацию. Требуются контрольные точки или устойчивые совпадающие объекты. Для трансформации сохраняются:

- модель преобразования: translation/rigid/similarity/affine;
- пары контрольных точек и их происхождение;
- RMS и максимальная остаточная ошибка;
- число и пространственное распределение точек;
- допустимость для выбранного вида расчёта;
- подтверждение специалистом.

OSM может предложить candidate transform, но не утверждать её автоматически. При недоказанной CRS слой показывается отдельно и не участвует в вычислении отступов.

## 6. Conflation: как не создать два здания

Для каждого CAD/официального контура ищутся OSM-кандидаты по буферу, затем считаются минимум:

- Intersection over Union;
- расстояние между границами и центроидами;
- отличие площади и ориентации;
- локальная согласованность смещения по соседним зданиям;
- конфликт существующего/снесённого/проектируемого состояния.

Результаты:

| Ситуация | Действие |
|---|---|
| Есть подтверждённый CAD-контур | CAD остаётся primary, OSM — дополнительное evidence |
| В CAD здания нет, OSM-контур согласуется с окружением | Создать candidate `structure.building` |
| Контуры расходятся больше допуска | `conflict`, исключить из автоматического safety-critical расчёта |
| Здание только проектируемое | Не переносить статус existing из OSM |
| OSM outline и parts | Один логический объект здания с составными геометриями, без двойного счёта |

Автоматический `ST_Union` источников запрещён: он скрывает конфликт и создаёт ложную точность.

## 7. Использование в ограничениях и 3D

Для preliminary planning контур OSM может формировать зону вокруг здания с явно записанной погрешностью и консервативным safety margin. Для нормативного решения, где ошибка положения может изменить допустимость посадки, возможны только три режима:

- подтверждение более точным источником;
- ручное принятие специалистом с документированным допуском;
- результат `needs_review`, не автоматическое разрешение.

Граница здания и буфер ограничения — разные геометрии. OSM поставляет candidate footprint; размер отступа задаёт конкретное опубликованное правило для типа посадки.

Для 3D OSM даёт footprint и, иногда, parts/высоту. Если высоты нет, интерфейс использует визуальный default, помеченный как synthetic. Такой объём разрешён для навигации и рендера, но не участвует в инженерных проверках освещённости или расстояний как измеренный объект.

## 8. Контроль качества

Импорт не публикуется, пока не пройдены проверки:

- файл PBF и конфигурация импорта имеют hash;
- импортёр и его версия записаны;
- все используемые polygon/multipolygon валидны либо сохранён журнал ремонта;
- нет оборванных relations на границе extract;
- `building` и `building:part` не дают двойного счёта;
- project CRS доказана, единицы — метры;
- для совмещения записаны RMS/max error и контрольные точки;
- источник не новее/старее проектного состояния без явной temporal policy;
- каждый созданный building имеет evidence и confidence;
- safety-critical запросы фильтруют неподтверждённые объекты и учитывают accuracy.

Отдельный отчёт по территории показывает: покрытие OSM зданиями, число принятых кандидатов, конфликты, распределение смещений, объекты без высоты и дату снимка.

## 9. Лицензия и атрибуция

Данные OpenStreetMap распространяются по ODbL. В интерфейсе, отчётах и экспортируемых материалах, где используются эти данные, должна присутствовать заметная атрибуция вида `© OpenStreetMap contributors` и ссылка на copyright/license page.

Архитектурная мера предосторожности:

- OSM-derived staging и его версии остаются логически отделимыми;
- для каждого канонического объекта сохраняется признак происхождения;
- экспортёр умеет сформировать перечень OSM-derived объектов и атрибуцию;
- перед публичной передачей смешанной базы или производной базы проводится отдельная проверка требований ODbL и share-alike;
- изображения/геометрия закрытых картографических сервисов не извлекаются без явно подходящей лицензии или API-соглашения.

Это техническая политика provenance, а не юридическое заключение.

## 10. Реализация прототипа

Контейнер `osm-importer` добавляется после миграции PostgreSQL на PostGIS. Он не входит в DWG-конвертер и получает отдельную очередь задач:

```text
register_snapshot -> verify_pbf -> import_staging
  -> clip_project -> validate_buildings -> propose_conflation
  -> human_review -> publish_canonical_model
```

В `osm2pgsql` используется современный Flex output: Lua-конфигурация создаёт только нужные таблицы и сохраняет исходные теги. Raw/staging таблицы доступны на запись только importer-role; основной сервис читает их и публикует новые immutable model revisions.

Первый эксперимент выполняется на двух пилотах. Успех — не просто наличие полигонов, а отчёт, отвечающий на вопросы:

- сколько отсутствующих в CAD зданий добавлено;
- удалось ли доказать общую CRS/трансформацию;
- какова ошибка совмещения;
- сколько конфликтов потребовало ручного решения;
- как повлиял OSM-слой на допустимую область посадки;
- воспроизводится ли результат из того же PBF и config hash.

### Отображение в web-приложении

Рабочее пространство предоставляет режимы `CAD`, `OSM`, `Overlay`, `Compare` и диагностический `Difference`. Overlay доступен как инженерный режим только для verified transform; candidate/rejected transform допускает лишь маркированный preview без измерений и принятия решений.

На карте постоянно показываются snapshot date, attribution, transform status, RMS/max error и working CRS. OSM-слой строится из локального PBF/PostGIS и собственного tile/feature pipeline. Публичные OSM tile servers не используются для массовой загрузки или offline cache. Полный UX-контракт описан в [задании на веб-приложение](13-web-application-design-brief.md).

OSM buildings являются кликабельными. Выбор не создаёт canonical object автоматически: пользователь добавляет feature в очередь рассмотрения, видит возможные совпадения и preview ограничений, а reviewer принимает его в новую draft model либо отклоняет. Полный workflow и API описаны в [контракте review зданий OSM](14-osm-building-review.md).
